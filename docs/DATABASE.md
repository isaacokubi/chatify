# Chatify Database

Core MongoDB collections are users, conversations, messages, memories, password resets and payments. Small relationships such as participants, admins, reactions, read state, notification preferences, and FCM device-token lists are embedded where practical. FCM tokens are excluded from user/API responses. Message notifications are sent through the notification provider and are not persisted as a separate collection.

Important indexes cover unique normalized user email, text search, conversation participants, a sparse unique canonical direct-conversation key, message conversation/createdAt and expiry fields, memory ownership, expiring one-use password-reset token hashes, unique internal payment IDs, payment participant/status lookup and provider checkout references. Payment records store requester/payer IDs, optional conversation, integer KSh amount, normalized phone, description, provider name/references, result and lifecycle timestamps. Callback processing uses a conditional update and callback timestamp for idempotency. MongoDB Atlas is the production database; no local database is assumed for deployment.


## School fee configuration and financial history

`SchoolFeeStructure` stores the current configuration for a school, normalized class key, academic year and term. A unique compound index prevents duplicate configurations for the same class-period. Each line item stores its amount as an integer number of minor currency units (KES cents), and the active-item total is stored in the same representation. Updates use an expected version to reject stale writes and retain up to 50 prior snapshots in the record. The history captures the previous version's items, total, status, updater and recorded timestamp.

A fee structure is **not** itself a student charge. Existing `SchoolFeePayment` documents are payment-ledger records identified by parent and student name; they do not currently reference a stable student enrollment, a charge item, or a fee-structure version. The new configuration endpoints therefore never rewrite existing payments or receipts and must not be used as an outstanding-balance source. Before automatic balances are introduced, add immutable student charge records linked to a stable student ID, class enrollment, academic period and structure version; model credits/refunds and confirmed payment allocations explicitly; then reconcile balances from those records and the existing confirmed-payment state machine. No data migration is required for the configuration collection itself; MongoDB creates its unique index when the schema index is initialized, and duplicate legacy records do not exist in this new collection.
