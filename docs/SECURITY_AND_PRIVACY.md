## Current boundary

The local MongoDB API integration uses synthetic users and confirms school-owner authorization for learner promotion/transfer, parent denial, and owner-scoped contact, Spark and memory deletion. It also confirms token/amount checks on platform, school and merchant payment callback routes. It does not establish complete cross-tenant coverage for every module, penetration-test certification, production secrets hygiene at the hosting provider, secure media deletion, or whole-application end-to-end encryption.

Callback tokens are carried in provider callback URL paths because provider callbacks do not provide a configurable authorization header. Server source does not log request URLs, but reverse proxies, hosting request logs, analytics and error-reporting products may record paths. Before configuring non-test callback tokens, the operator must confirm those systems redact callback route paths; this cannot be verified from the repository. Keep these tokens distinct, random and at least 32 characters, and rotate on exposure. Never include full callback URLs in support tickets or reports.

The disposable-database integration URI fails closed unless it uses the `mongodb:` protocol, no credentials or URI options, exact loopback `127.0.0.1:27018`, and an allow-listed audit database name. Its teardown shuts down the API and closes the connection before dropping that database. Integration and index migration used localhost-only ephemeral MongoDB 7 instances. The backup/restore evidence verified the local archive checksum, 23 restored collections and one synthetic probe in another ephemeral server; it did not verify encrypted offsite backup custody or production access controls. These guards reduce accidental exposure but cannot prove that an operator has not deliberately forwarded a production database onto the approved local port. Record actual static/test results and remaining external review requirements in `docs/TEST_RESULTS.md` before release decisions.

Daraja callback configuration is validated before provider initialization. Provider boundaries: the current email adapter is SMTP/Nodemailer only; it does not implement Resend. Required `SMTP_URL` and `SMTP_FROM` settings are missing, so no live email was sent. Cloudinary validation/provider behavior is covered by mocks; credentials exist, but the current uploader targets the normal `chatify` folder and no live upload was made. FCM test coverage uses injected transports, while the configured environment lacks an FCM project ID and service credentials, so live push delivery was not attempted. Genuine Daraja sandbox OAuth passed with a token-redacted HTTP 200 response; STK and provider callback delivery remain unverified.

School receipt email uses a database claim to suppress concurrent duplicates and clears the claim on reported delivery errors. SMTP does not expose a provider-side idempotency key in this implementation, so a process crash after SMTP accepts a message but before the database records that acceptance can still make a retry send a duplicate. This is an external delivery boundary and needs an idempotent mail provider or operational reconciliation before strict exactly-once email delivery can be claimed.

## Kenya release review

Current official sources reviewed on 2026-10-25: the [Kenya Data Protection Act](https://new.kenyalaw.org/akn/ke/act/2019/24/eng%402019-11-15/source) includes specific requirements for children's personal data, including parent/guardian consent and best-interests safeguards; ODPC publishes [registration guidance](https://www.odpc.go.ke/faqs/) and [data-subject rights](https://www.odpc.go.ke/rights-of-a-data-subject/). Chatify's school module handles student and guardian information. The operator must document its controller/processor role, any applicable registration/exemption, notices/consents, retention, and child safeguards with the responsible Kenyan privacy/legal adviser. This source review does not establish compliance.

CBK describes the authorization and oversight framework for payment service providers in its [National Payment System guidance](https://www.centralbank.go.ke/national-payments-system/). Whether it applies to Chatify depends on the real legal entity, money flow, custody/processing role and commercial model; get an owner/legal determination before launch. This code audit does not claim CBK authorization or Safaricom approval.
